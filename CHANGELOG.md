# Changelog

All notable changes to the images. Exact upstream versions are in each release's `VERSIONS.md`.

## [Unreleased]
- **Mesh shaders on the original PS5 and Slim, per game (experimental): DirectMesh as a second RADV.** [DirectMesh](https://github.com/lonewolf0622/Mesh-Shaders-for-Rdna-1-) adds `VK_EXT_mesh_shader` (with Task shaders, barycentrics and device-generated commands) to RADV on GFX1013, written for the BC-250, whose GPU is the PS5's family. `bootc/mesa/build-radv.sh` builds it 64-bit from its own tree at `directmesh-v1.4` (`cac0bcc`, Mesa 26.2.1) with Bazzite's three Mesa patches and `bootc/mesa/directmesh/0001`, which adds the PS5's PCI id (`13fb`) to the list it turns itself on for; it goes to `/usr/lib64/directmesh/` with its own ICD manifest. `ps5-directmesh %command%` as a Steam launch option sets `VK_DRIVER_FILES` to it for that game; 32-bit programs and everything else keep the system driver, and on a PS5 Pro the launcher changes nothing. Not merged into the system RADV: the patch (30,747 lines) doesn't apply to 26.2.6, and 27 places change GFX1013 behaviour without Mesh shaders. v1.4.1 is withdrawn upstream for GPU hangs, so the pin is v1.4. Compiled here with the image's meson options (0 undefined symbols); not run on a PS5
- **Legacy installs are no longer supported, from v2.13 on.** No update bundle is built (`release.yml` loses its bundle job, `tools/update.sh` and `tools/make-update-bundle.sh` are gone), the notes have no Legacy section (`tools/release_notes.py` renders one format), and `tools/update-latest.sh`, the Legacy update command, prints the notice and the way to switch. The v1.8.9 notes and `docs/update-sections/` are gone. `ps5-report` says so on a Legacy install's Install line. v2.13 itself is unchanged
- **`tools/legacy-to-bootc.sh` converts a Legacy install to bootc in place.** `bootc install to-existing-root` wipes `/boot` and always runs bootupd, which has nothing to install on a PS5; the script does what the image builders do instead: `ostree admin init-fs` and `os-init` on the running root, `ostree container image deploy` of `:stable` with `root=UUID=… rw`, the image's `kargs.d` arguments appended to the boot entry, then `ps5-bootc-sync` writes the loader's files as for a disk image. Users with a login (uid 1000 to 59999) come over with their password, groups and subuid ranges, as do the hostname, machine-id, time zone, locale, saved networks, SSH host keys and `/etc/ps5-bazzite-deck`. A one-time unit moves home folders, Flatpaks and Bluetooth pairings at the first bootc start, by rename inside `/sysroot`. Nothing of the Legacy system is deleted before `--cleanup`; its kernel, initrd and `cmdline.txt` wait in `legacy-backup/` on the boot partition, and `--undo` puts everything back before the first bootc start. Tested: `bootc/tests/legacy-to-bootc.sh` (15 cases: accounts, kernel arguments, the first-start move), the ostree layout commands on a scratch folder. Not tested: the image deploy and a first start, which need a console
- **The image's file list is `bootc/build_files/files.list`** (it lived in the Legacy bundle script); the build installs the same 41 files to the same places

## [v2.13] – 2026-11-12
> Pre-release. What the loader reads from the PS5 reaches Linux in the initrd: a PS5 Pro has 60 compute units from the first start, and starts without a USB drive get Wi-Fi firmware and pairings.
- **The loader appends what it dumps to the initrd** (`loader/patches/0005`). It dumps the PS5 Pro GPU firmware, the IW620 Wi-Fi firmware and the Bluetooth pairing export next to the initrd it loaded, and Linux picked them up from the boot partition later: the GPU firmware only on the start after (`ps5-stage-viola-fw` appended it to the boot partition's initrd), and none of them when the boot files are in `/data/PS5/Linux`, which Linux can't read. A Pro started that way ran as a base PS5, 36 compute units and no GPU clock governor (the PS5 Pro report of the GPU stuck at 500 MHz). The loader now appends a newc archive to the initrd in memory: the GPU firmware where amdgpu loads it, the Wi-Fi firmware and the pairing export under `/ps5` in the boot directory's layout. Each part goes in whole or not at all; with nothing to add, the initrd is unchanged. The initrd buffer keeps 8 MiB for it. Tested on this side: against a real dracut initramfs in seven cases under ASan/UBSan, the archive unpacking to the dumped files byte for byte with the intended modes (the GPU part as the script's archive); the loader build passes its checks (shellcode headers byte-identical, no new warnings)
- **`ps5-dumps`, a dracut module,** copies `/ps5` to `/run/ps5` before the initramfs ends, and the appended GPU firmware to `/run/ps5/lib/firmware/amdgpu/`: the boot partition's layout. `ps5-stage-firmware` (the image build adds `/run/ps5` to its search list, with a build check) and `ps5-bt-import` look there first, then on the boot partition as before; after importing from `/run/ps5`, `ps5-bt-import` deletes the export on the boot partition, as the importer does with the copy it reads. The image build checks the module is in the initramfs. `ps5-report` lists what arrived in `/run/ps5`
- **Warm reboots keep the PS5 Pro GPU firmware:** `ps5-kexec` starts the boot partition's initrd without the loader, and that initrd no longer carries the firmware; it now appends the same archive from `/run/ps5` in memory (a memfd) when all eight files are there, and loads the initrd as is otherwise. Tested on a real initramfs: the archive walks and unpacks like the loader's
- **`ps5-stage-viola-fw` is gone,** and with it the `ps5.viola_cp=cs2` option. Legacy updates disable and delete it, its state file and `initrd.img.noviola`; `ps5-bootc-sync` removes a leftover `initrd.img.noviola`
- Rebase for X.Y: rmux's default branch (`shitshow` at `8de2aff`) and soniciso1's loader (`main` at `9ffe824`) are unchanged since the pins, so nothing moved

## [v2.12.1] – 2026-11-11
> Pre-release. 4K120 is no longer withdrawn by a link check that outlived its link.
- **The 4K120 link check ends when a modeset begins** (`patches/ps5-display.patch`, `drivers/ps5/hdmi.c`). After a 4K120 setup the driver polls the bridge for up to 5 s and, if the FRL link isn't up, stops offering 4K120 for that display until another EDID arrives or the kernel restarts. That rule is unchanged. The check was only ended by the next video setup, at its end: a modeset that takes the link down without a setup after it (the commit's first block mutes and re-initialises the bridge for the new or the old stream; the setup runs only with a new stream), or an output going down, left it polling a link that was taken down on purpose, and it withdrew 4K120. It also read its sequence number when it started, 1.5 s after being queued, so a modeset inside that time didn't end it either. `sceHdmiDeviceSetVideoMute(1)`, which every modeset begins with and nothing else calls, now cancels a queued check and invalidates a running one; the increment at the end of the setup is gone. Reported after a switch from Game Mode to Desktop: `4K120 link didn't come up (0x7019=00)` 6.7 s after a setup, after eight links that came up, with the output still marked active in 4K120 and no setup logged in between. The case fits; it is not confirmed on the console yet

## [v2.12] – 2026-11-11
> Pre-release. M.2 installs no longer end in the emergency shell after an update; Steam's About page names the release.
- **A deployment under the other ostree boot version** (`ps5-ostree-path`, a dracut module in the initramfs, before `ostree-prepare-root`): `cmdline.txt` names the deployment as `/ostree/boot.N/default/<checksum>/<n>`, and ostree keeps that N both in `/boot` and in the root. On an M.2 install those are two drives, and two consoles ended in the emergency shell after updating to v2.10 with `Couldn't find specified OSTree root '/sysroot//ostree/boot.1/…'`: the root had the same deployment, same checksum and index, under `boot.0` only. When the named `boot.N` is missing and the other one holds that exact deployment, it is linked to the other's folder; `ps5-bootc-sync` then rewrites the boot partition and ostree's next cleanup removes the link. Nothing happens for a deployment the root doesn't have. Why the two counters part is not established (the reports show the root's side only). `bootc/tests/ps5-ostree-path.sh`, 10 cases; CI now runs every script in `bootc/tests/`
- **Steam → Settings → System → About:** OS Variant `ps5-bazzite-deck` and OS Build the channel and the release, `Stable 2.12` or `Beta 2.12` (`VARIANT_ID` and `BUILD_ID` in `os-release`, the channel as a `CHANNEL` build argument and the release from `git describe`; a release tag's own image goes by whether that release is a pre-release). OS Name and OS Version stay Bazzite's: `VERSION_ID` is Fedora's release (45), which `toolbox`, systemd extensions and package tools read, and Bazzite's own build carries it over for that reason. `NAME` and `PRETTY_NAME` are no longer replaced, so `fastfetch` says Bazzite; the release is in `ps5-report` and `/usr/share/ps5-bazzite-bootc/VERSION`
- **`patches/upstream/`:** three single-topic changes for rmux's repository (SDR metadata in his FRL planner, `ps5-cpufreq` rate limit, `ps5-cpufreq` not on the Pro), each applying and compiling on his tree at Linux 7.3.1. `tools/upstream-pr.sh` builds them on upstream's kernel version (`KERNEL_REF` in its `build.cfg`), stops unless upstream's `linux.patch` regenerates byte for byte, needs `--tested` to submit, and states in the pull request that it was prepared with AI assistance
- `ps5-cpufreq.patch` without the Pro GPU ceiling, which the driver no longer uses once it stays off the Pro
- `patches/upstream/`: the Pro Bluetooth setup for rmux's repository, and the IW620 TDLS change for ps5-linux-mwifiex with its apply line for ps5-linux-image; `tools/repo-pr.sh` opens a pull request from a change set against a repository without a `linux.patch`
- **The build's check that the initramfs has `ps5-ostree-path`** reads a saved listing. Piped into `grep -q` under `pipefail`, the listing command was cut off at the match and the pipeline counted as failed: the first v2.12 image build stopped at `initramfs without ps5-ostree-path` although the module was in. No v2.12 image was published before this

## [v2.11] – 2026-11-11
> Pre-release. Starts on PS5 system software 4.x, cooler at idle (CPU and GPU clocks), Wi-Fi no longer dies on a TDLS request; one kernel patch per feature.
- **bootc drives on PS5 system software 4.x** (`bootc/tools/gpt-first-lba.py`, run by `finish-disk-image.sh`; cause found and proven by fitamix, confirmed by numitors): bootc-image-builder writes the GPT with first usable LBA 2048. The 4.x kernel sizes its walk over the partition entries from that field, reads about 8,184 entries where 128 exist, the table fails its check and no partition appears: "unknown format" on the PS5, "Couldn't find bzImage" from the loader. The disk image now has 34, as the Legacy images did. The same tool fixes an image or an already flashed drive (dry run unless `--apply`), and `bootc/tests/gpt-first-lba.sh` runs in CI
- **Fresh installs of a stable release follow Stable:** the disk image was built while its release was a pre-release, so its installs followed `:beta` for good. Promoting a release now builds its disk image again, for `:stable`
- **CPU at idle** (`patches/ps5-cpufreq.patch`; found and measured by fitamix): `ps5-cpufreq` sets `transition_delay_us` to 10 ms. From its 50 µs latency alone schedutil re-evaluated every 75 µs: about 275 P-state requests a second to MP1 at idle, `sugov:0` the busiest task, the cores at 2.3 to 2.6 GHz with nothing running. At 10 ms they rest at 800 MHz and games still reach the full clock
- **GPU clock after CPU boost** (`patches/ps5-gpu.patch`; reported from a Slim that idled at 62 °C until its GPU clock was set again, then 46 °C): MP1's universal mode, entered every time a boost frequency is chosen, sets a GPU clock range of 2,000 MHz and up. The governor's cached clock was then stale and an idle GPU stayed at 2 GHz, because 500 MHz looked already set. `mp1.c` now tells `ps5-gpufreq` after entering or leaving that mode, and the next poll (50 ms) requests the governor's clock again
- **IW620: no TDLS** (`patches/mwifiex/ps5-iw620-no-tdls.patch`, applied after the ps5-linux-mwifiex patches; reported with four boot journals): the console's firmware rejects `TDLS_OPERATION` (0x122), so a phone on the same network that started a direct link (opening Sunshine's web page was the trigger) ended in a disconnect and a scan command that never returned, with Wi-Fi gone until the driver was rebound. The driver no longer advertises TDLS, so `wpa_supplicant` declines and the peer keeps going through the access point. `build.sh` applies every patch in `patches/mwifiex/` after the builder's own
- **Salina xHCI kept out of runtime D3** (`patches/ps5-bluetooth.patch`, ps5-linux-patches #78 by Slip): it didn't come back from it, and the Bluetooth chip on it was lost until a cold start
- **Wi-Fi follows the access point's country** (image builder at `03b59ab`, ps5-linux-image #52; Wi-Fi driver at `3d81cba`, ps5-linux-mwifiex #12): `country_ie_ignore=0 beacon_hints=0`, so the IW620 leaves the restrictive world regulatory domain; the driver gains `ps5_fake_connected_scan` (default 1, as before)
- **Kernel patches: one per feature, 6 instead of 13.** `ps5-display` takes in the HDMI modes, the test switches and the triple-buffer fix; `ps5-gpu` the KFD TLB flush and the clock resync; `ps5-cpufreq` the rate limit and the Pro's exclusion; `ps5-bluetooth` the Pro, MediaTek and IW620 fixes and the Salina xHCI. The resulting kernel tree is byte-identical to the 13-patch series
- **Not taken from #78: its GPU sensors.** The display stack has exported `gpu_busy_percent` and an amdgpu hwmon with the temperature since v2.1.x (`amdgpu_dm.c`), which is what overlays read; a second export of the same file would be a duplicate-filename warning at every start
- **`usbcore.autosuspend=-1` no longer in the bootc kernel arguments:** the kernel has been built with `CONFIG_USB_AUTOSUSPEND_DELAY=-1` since v1.5.1, so v2.10's argument changed nothing
- Loader patches without `Co-Authored-By` trailers

## [v2.10] – 2026-11-10
> Stable. Switches to test which display fixes are still needed; HDR no longer offered on VERDE; USB autosuspend off on bootc. As stable, it brings v2.8 to v2.9 to the Stable channel.
- **Display test switches** (`patches/ps5-hdmi-switches.patch`): `hdmi.rearm`, `hdmi.edid_keep`, `hdmi.scdc_writes`, `hdmi.sleep_mute`, all on and changeable at runtime, each turns off one delta this display stack has over rmux's tree (off, `sleep_mute` re-initialises the video setup as his tree does). `ps5-report` shows them; `docs/testing.md` has the test per switch. The ones that make no difference go; the ones that do go upstream
- **VERDE: no HDR offered** (same patch): neither the official tree nor rmux's has an HDR setup for VERDE, nor did v1.8.9, so the TV was never told and HDR content came out washed out (reported on a Slim with an LG C2, while the Pro was fine from the same drive). FLAVA3's HDR path is unchanged since v1.8.9. The HDR Static Metadata block is dropped from the EDID on VERDE, so neither Game Mode nor the desktop switches to HDR
- **bootc: `usbcore.autosuspend=-1`**: USB SSDs can drop off or reset when USB autosuspend suspends them, and the system runs from one (as in the CachyOS PS5 guide)
- `update.sh` no longer removes `hdmi.rearm=` from `cmdline.txt`, which is a switch again

## [v2.9] – 2026-11-10
> Pre-release. Controllers paired in the PS5 system connect in Linux without pairing; compute through KFD; newer image builder.
- **PS5 pairings in Linux** (`loader/patches/0004`, ps5-linux-loader #97 by Slip; `ps5-bt-import`, `tools/fetch-bt-sync.sh`): the loader writes the PS5 system's active Bluetooth pairings to `ps5-bt-sync.json` next to the initrd at every start, and upstream's importer (`bluetooth/ps5-bt-sync` from ps5-linux-patches, fetched at a pinned commit and checksum, not kept in this repository) merges them into BlueZ before Bluetooth starts. The export carries no adapter address, so `ps5-bt-import` runs the importer only while Linux uses the PS5's own address and deletes the handoff otherwise: with the Linux-only address on, the PS5's keys would replace working Linux pairings. `ps5-bt-address is-on` gives that state as an exit status. Not for boot files on the console's own storage (`ps5-m2-install --boot`), where Linux can't read the handoff
- **Compute through KFD (ROCm/HIP, OpenCL)** (`patches/ps5-gfx1013-kfd-tlb.patch`, ps5-linux-patches #57 by Tertium and #77 by Sergey): the GFX1013 PASID TLB flush, which rmux's tree had dropped, with the fix that flushes every KFD VMID when the PS5 maps none; stale translations caused page faults and lost writes. Games (Vulkan) don't use KFD
- **Image builder at `7ab490a`** (was `52db0a4`): it now applies the Wi-Fi driver's patches for this kernel, sets `ext_scan=2` and keeps objtool itself, so `build.sh` only pins the driver commit; its patches mount, unused by the builder all along, is gone. An importer unit a future kernel RPM may enable is switched off in the image (`ps5-bt-import` gates it)
- **Warm reboots and `bootc rollback`** (`ps5-bootc-sync --is-current`, bootc drop-in of `ps5-kexec-prepare`): with warm reboots on, a restart after a rollback or after new kernel arguments came back on the deployment that was running, because the kernel was loaded from the boot partition before the sync rewrote it at shutdown. The unit now only loads it while the boot partition holds the default deployment; otherwise the restart goes through the PS5 system and the loader
- `ps5-report` shows the pairing import; the weekly upstream audit reports new upstream commits for the importer and the builder
- Workflows: `actions/checkout` v7, `upload-artifact` v7, `download-artifact` v8
- `ps5-bt-addr`: `mkdir` without the one-use function

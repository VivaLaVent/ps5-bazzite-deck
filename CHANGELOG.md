# Changelog

All notable changes to the images. Exact upstream versions are in each release's `VERSIONS.md`.

## [v2.16] – 2026-11-15
> Pre-release over v2.15. Native resolution from the first start; one DualSense pairing for the PS5 and Linux on every console; the Pro's GPU limit at 85 °C; Wi-Fi without country following; drivers for the Xbox Wireless Adapter, Xbox Bluetooth controllers, racing wheels and streaming; a GPU hang no longer takes the display down; the VRAM scanout test gets its missing second option; `ps5-report` stops flagging files tuned and Steam rewrite.
- **No full GPU reset on the PS5** (`patches/ps5-gpu-reset-guard.patch`, from the official ps5-linux-patches #81, tested there with GPU hangs on a PS5). `amdgpu_device_should_recover_gpu()` returns early on GPUs without RAS, so the existing Cyan Skillfish exclusion was never reached, and a failed ring reset escalated to a MODE1/PSP reset, which doesn't work on a PS5: seen on a PS5 Pro in BeamNG.drive on v2.15 (`Ring gfx_0.0.0 reset failed`, `MODE1 reset`, `ring kiq_0.2.1.0 test failed (-110)`, `GPU Recovery Failed: -110`, then pageflip timeouts until a restart). With the default `gpu_recovery=-1` the PS5 now stops after the per-queue reset; `amdgpu.gpu_recovery=1` still allows the full reset. Five lines; `amdgpu_device.o` compiles. Not run on a console here
- `ps5-report` no longer lists `/etc/modprobe.d/tuned.conf` and `/etc/NetworkManager/conf.d/99-valve-wifi-backend.conf` as changed on the console: tuned and Steam's Wi-Fi settings rewrite them themselves
- **PS5 Pro on 13.00: the GPU firmware offset** (`loader/patches/0006`, from the official ps5-linux-loader badfe48, #104, tested there on a retail Pro with 13.00: all 8 blobs dumped, 60 CUs). Our base (soniciso1's fork) has the rest of that commit, 13.00 in the Pro hypervisor adjustment, but not `PS5_PRO_GPU_FW_OFFSET` in `off_1300`, so a Pro on 13.00 ran on 36 CUs. One line; the loader build passes its checks (shellcode headers byte-identical, no new warnings)
- **`ps5-report` lists the base's versions** of gamescope, Mesa, NetworkManager, wpa_supplicant, linux-firmware and steamos-manager in the bootc section: several regressions reported since v2.13 have no matching change of ours, and the image takes Bazzite's updates daily
- **An image builds without DirectMesh when its source is gone** (`bootc/mesa/build-radv.sh`, `bootc/build_files/build.sh`): the image build cloned DirectMesh from its author's repository and stopped when the clone failed or the tag no longer named the pinned commit, so a deleted or retagged repository (as happened to rmux's) would have stopped every image over an optional per-game driver. Now it builds without DirectMesh with a warning, `VERSION` records `directmesh=none`, and `ps5-directmesh` falls back to the system driver, as it already does without the files. A build failure of a source we do have still stops the image. Tested with stand-ins for the four cases (source gone, tag moved, normal build, compile failure) and for the install step with and without the files
- **The display's own preferred resolution at 60 Hz as the preferred mode** (`patches/ps5-display.patch`, `ps5_hdmi_add_modes()`): every display started at 1080p60, desktop and Game Mode alike, so games started at 1080p unless the user changed it. Now the sink's preferred resolution is taken at 60 Hz in one of the bridge's standard setups (1080p60 CTA 16, 1440p60 2720 total, 2160p60 CTA 97), never a manual or FRL timing, and only within the sink's own TMDS limit (an EDID listing 4K60 with a lower `max_tmds_clock` would otherwise make a mode preferred that its link can't carry); 1080p60 when there is none. `amdgpu.force_1080p=1` remains the way back. A resolution the user chose stays (KDE's and Steam's saved settings); without one, the next start uses the native resolution, so on a 4K TV games render at 4K by default. `hdmi.o` compiles without warnings, and the patch's `hdmi.c` section reverse- and re-applies byte for byte on the compiled file; checked against the EDIDs of this week's reports (G60SD 1440p60, PG27UCDM 2160p60, a Samsung TV 1080p60). Not run on a console
- **PS5 Pro: GPU limit 85 °C, as on the other models** (`files/ps5-console-defaults`). The Pro got `ps5_gpufreq.temp_limit=80`, the same as the fan's 80 °C target, so the GPU throttled whenever the fan held its temperature (seen in Micael's reports). New installs get no limit of ours (the kernel's 85 °C); existing ones have exactly `ps5_gpufreq.temp_limit=80` removed from `cmdline.txt` once, any other value is kept. Tested on eight command lines
- **Wi-Fi (IW620): the driver's own regulatory defaults** (`bootc/build_files/build.sh`): the kernel package's `moal.conf` sets `country_ie_ignore=0 beacon_hints=0` (from ps5-linux-image #52, in v2.11), so the driver adopted the access point's country. Reverted to the driver's defaults (1, 1) by removing that line in the image, with a build check. No reported problem was traced to it with data, and there was no reported need for it
- **Bazzite's out-of-tree drivers for games and streaming, built for our kernel** (`bootc/kmods/`, a new build stage, `modules.list`): Bazzite builds them for its own kernel and its `kmod-*` packages go with it (`build.sh` removes them with Bazzite's kernel), so they were all missing. Built against the build tree in our kernel package, at pinned commits: xone v0.5.8 (Xbox Wireless Adapter: the adapter's driver and the protocol drivers, 8 modules, not `xone_wired`, which would compete with the kernel's `xpad` for controllers on a cable; `mt76x2u` not blacklisted, as it runs MT7612U USB Wi-Fi sticks, so it still claims the two oldest adapter IDs 02e6/02fe), xpadneo v0.10.5 (not in Bazzite; with its udev rules and module aliases), new-lg4ff v0.5.0, hid-tmff2 0.83 (`hid-tmff-new`, not its hid-tminit, as Bazzite), t150 1.0, hid-fanatecff 0.2.3, gcadapter-oc v1.4, v4l2loopback v0.15.4, openrazer v3.12.4 (the four driver modules; the daemon is Bazzite's). Their udev rules and options come with Bazzite's packages, which aren't `kmod-*`. Bazzite's `/usr/lib/modprobe.d/new-lg4ff.conf` blacklists the kernel's `hid_logitech` for new-lg4ff, so Logitech wheels most likely had no driver on our image; the build now keeps the two together (blacklist with new-lg4ff, none without). Each driver is optional: a source that is gone, a tag that no longer names the pinned commit, or a build failure leaves only that driver out, with a warning; missing prerequisites (the build tree in the kernel package, `rpm2cpio`/`cpio`, installing gcc and make) leave all of them out with a warning, never the image; `VERSION` lists what is in (`kmods=`), and `ps5-report` shows it. The adapter firmware check warns when Bazzite's base has none. Tested with the real script against the real v2.14 kernel package (gcc 14): all nine build in under a minute, 19 modules with `vermagic 7.3.3-viva`; a moved tag and a failing build each drop only that driver; a missing kernel package and a failing compiler install drop all, with exit 0; the install step with all, none, and the four blacklist cases. Not run on a console
- Async compute on the original PS5 and Slim stays on, with its switch documented: `AMD_PS5_COMPUTE_QUEUE=0` per game or system-wide (`AMD_VIOLA_COMPUTE_QUEUE=0` on a Pro)
- `ps5-user-defaults` reviewed: once per user, retried at each login until Steam exists, user videos kept, only Bazzite's identical overrides deleted (tested); Steam's own videos are copied as overrides, so a later Steam update of them doesn't show, which is the price of the design
- **The Linux-only Bluetooth address is gone: every console shares the PS5 system's pairings** (`files/ps5-bt-addr`, `ps5-bt-pro-addr`, `ps5-bt-address` and their two services removed; `ps5-bt-import`, `ps5-kexec`, `ps5-report`, `99-ps5-bt-services.rules`, the services' ordering). The address predates the loader's pairing export (v2.9, ps5-linux-loader #97). On the Slim it has been off since v2.8.1 because it broke connections on several units; on the original PS5 and the Pro it stayed on by history, and the import works there (a Pro on v2.15: 3 pairings imported). It cost a second controller profile, on the IW620 the warm reboot (the chip hangs with a changed address), and about 300 lines of chip-specific code. `ps5-bt-import` now always imports; `ps5-kexec` no longer turns warm reboots on the IW620 into normal ones: an update applies through a normal restart, which brings the chip back to its own address, and nothing sets another one. Who had it: the controller's PS5 profile works in Linux; devices paired only in Linux pair once more. `tools/legacy-to-bootc.sh` still recognises a Legacy install by its `ps5-bt-addr`
- **Release notes: each fix announced where it last happened** (`docs/release-notes/v2.7`, `v2.7.3`, `v2.8`, `v2.8.1`, `v2.10`): fixes that a later release had to make again are no longer claimed in the earlier notes: the fan target (v2.7 and v2.7.3, settled in v2.8.1 and v2.10), the IW620 connection that "fails at once instead of hanging" (v2.8, fixed in v2.15), and the Linux-only Bluetooth address on the Slim (v2.7, v2.8.1, v2.10, gone in v2.16). A stable release that repeats its pre-releases' fixes is the same fix on another channel and keeps them
- **Leaner build and image** (no change in behaviour): the kernel config edits in `build.sh` go through one function instead of three different forms, one option set twice (the resulting option set is identical, checked on rmux's config at the pinned commit); `ps5-stage-gpu-firmware` is removed from the image instead of path-fixed and then disabled (it writes to read-only `/usr`); the `bluetooth.target.wants` links that `systemctl enable` already makes and the second identical USB power rule for the MediaTek Bluetooth chip (`99-ps5-bt-phantom.rules`; `99-ps5-usb-power.rules` keeps it) are gone; `patches/upstream` is emptied: the TDLS fixes were merged upstream, the SDR metadata fix is in the official #81, and the rest went with rmux's repository
- `ps5-stage-viola-fw.service.d/10-after-bootc-sync.conf` removed: the unit it extended went with v2.13
- Upstream audit for this release: soniciso1's loader `main` and the official ps5-linux-patches are at our pins' state (the official tree's newer work comes with the planned kernel move); the official Wi-Fi driver and image builder moved only to adopt our TDLS fix (byte-identical to `patches/mwifiex/ps5-iw620-no-tdls.patch`), so their pins stay; Bazzite still ships Mesa 26.2.6 (no mismatch warning in the image builds), so RADV stays on 26.2.6 although 26.2.7 is out; DirectMesh has no release after the withdrawn v1.4.1; pahole 1.31 and 1.32 are out, the builder still uses Debian's 1.30 (sched_ext, planned separately)
- **The VRAM scanout test needs `amdgpu.sg_display=1` too** (`patches/ps5-scanout-fallback.patch`). The PS5's display IP is 2.0.3 (`amdgpu_discovery.c` sets it under `CONFIG_X86_PS5`), and for that version `amdgpu_dm` turns S/G display on only with `amdgpu.sg_display=1`; the fallback requires S/G display, so `ps5_scanout_gtt=1` alone never ran, and the hint it logged instead told people to set the option they had set (reported with Ratchet & Clank: Rift Apart on v2.15). The hint now names what is missing; the v2.15 notes and the wiki give both options. The v2.15 review had called S/G display "on" without checking the IP version

## [v2.15] – 2026-11-15
> Pre-release over v2.14. The IW620 Wi-Fi freeze, 1440p at 100 and 120 Hz on FLAVA3, a test switch for games dropping out of Game Mode when VRAM is full, DirectMesh on every base PS5, a shell in emergency mode, `ps5-report` showing local changes. v2.14.1 and v2.14.2 were withdrawn before they were complete; their changes are here.
- **IW620: a remain-on-channel request no longer waits for ever** (`patches/mwifiex/ps5-iw620-roc-bounded-wait.patch`; issue #60, ziernaht). With host MLME the driver asks the firmware to stay on the channel before it sends authentication frames, and waited for the answer with `MOAL_IOCTL_WAIT`. When that command times out, `woal_ioctl_complete()` prints "IOCTL: command timeout" and leaves such a caller asleep, expecting a firmware reload that the PS5 has switched off (`auto_fw_reload=0`); cfg80211 holds the wiphy mutex meanwhile and NetworkManager holds RTNL waiting for it, so every network call on the console hung in D state until a restart. The request now uses `MOAL_IOCTL_WAIT_TIMEOUT`, whose caller is woken with the error (after 20 s at the latest): the connection attempt fails, the console keeps working. The request stays allocated while pending and its wait queue is part of it, so a late answer finds valid memory. Applies after ps5-linux-mwifiex's patches in either order with ours; `moal_ioctl.o` compiles against the PS5 kernel tree. Not run on a console
- **Beta's kernel pin back on v2.14** (`bootc/pins.env`): it pointed at v2.14.1's kernel RPM, which goes with that release. The file is byte-identical to v2.14's again; v2.15's release moves Beta to its own kernel
- **`ps5-report`: "Changed on this console"**, a section with what is not the image's own: kernel options added to the image's, kernel modules loaded from outside the image (with the taint value), ps5-linux-tools' `ps5fan`/`ps5boost` services, packages layered with rpm-ostree, and driver or network settings that differ from the image's in `/etc`. Several reports this week turned out to depend on such changes (`ttm.pages_limit`, a second fan control, a hand-loaded module). The display line reads the CRTC that shows a picture: with the first CRTC off it printed ": 0Hz"
- **`tools/legacy-to-bootc.sh`, two failure cases:** a second `--apply` after a failed one would have set up accounts in the first deployment (`<checksum>.0`) while ostree starts the second; an earlier attempt's `/ostree` now stops the script with a pointer to `--undo`. And the Legacy kernel and initrd are put back on any exit between moving them to `legacy-backup/` and the end of the switch (a failure between the two moves left one behind). Two more test cases
- `ps5-m2-install` ends with the step for starting without the USB drive (`--boot`); leaving it out ends in emergency mode
- **A shell in emergency and rescue mode.** root has no password on the image, so when a start stopped there (a required mount missing, for example `/boot` on an unplugged USB drive) the console said "Cannot open access to console, the root account is locked" and offered nothing. `SYSTEMD_SULOGIN_FORCE=1` for `emergency.service` and `rescue.service` gives a root shell at the console instead, as the initramfs already does. Someone at the console already has `ps5`/`ps5` with sudo, so this opens nothing new
- `ps5-report` listed `/run/ps5` without root and printed `find: '/run/ps5': Permission denied` instead of the files the loader handed over (the folder is root-only, for the pairing keys); it uses `sudo` now, as for the rest of the report
- **FLAVA3, 1440p above 340 MHz (100 and 120 Hz): the mode's own timing, through the manual setup** (`patches/ps5-display.patch`, `drivers/ps5/hdmi.c`). Every 2720-wide 1440p mode went through the bridge's 1440p preset, which is its 60 Hz setup, and `ps5_hdmi_fixup_timing()` moved the syncs of every 1440p mode to that setup's back porches (80 px, 33 lines). At 60 Hz those are the timing's own; at 120 Hz the back porch is 77 lines (155 in the 2880x1608 timing some monitors prefer), so the picture started 44 or 122 lines early: shifted up, or out of bounds. Seen on an LG TV at 1440p100/120 and on an Odyssey G60SD on a Pro (hwdnick), whose `ps5-report` had the EDID and the sync positions sent: `vsync 1487-1492` where the EDID's 120 Hz timing has `1443-1448`. Now FLAVA3 uses the preset up to 340 MHz only, and above it the bridge gets the mode's timing by the manual setup with the syncs where the sink's timing has them (VERDE has no manual setup and keeps its 1440p setup at every rate, as before; a first version of this change took 1440p 100/120 away from VERDE, found in review); the polarity is still made the standard +hsync -vsync. That is what the official ps5-linux-patches do (stock 1440p setup for the 60 Hz clock, manual above 340 MHz, no sync changes), where 1440p120 is tested. 60 Hz timings are unchanged: checked with the functions built into a test on the G60SD's modes (CVT-RB 60 Hz and the EDID's 2880x1608 60 Hz come out as before; 100 and 120 Hz keep their syncs and get `vstart` 68, 83 and 166). `hdmi.o` compiles; not run on a console
- **A test switch for games dropping from Game Mode to the desktop when VRAM is full** (`patches/ps5-scanout-fallback.patch`, `amdgpu.ps5_scanout_gtt=1`, also at runtime in `/sys/module/amdgpu/parameters`). amdgpu pins every frame it shows as one contiguous block of VRAM unless the buffer was created write-combined, which a game's swapchain isn't. With the PS5's fixed VRAM carve-out, a game that fills it leaves no room for the next frame: `Failed to pin framebuffer: -ENOMEM`, gamescope aborts, and the session falls back to the desktop (Predecessor, Expedition 33; most often at 4 GB VRAM; issues #63 and #64). With the switch on, such a pin is retried in GTT (asked for alone, because `amdgpu_bo_pin()` narrows a VRAM|GTT request to the buffer's preferred VRAM); Cyan Skillfish with S/G display only, not for the cursor. Off by default: amdgpu allows GTT scanout only for write-combined buffers because other placements hung the display on some APUs, and whether the PS5 is one is not known. Without the switch the first such failure logs a hint. Compiled; not run on a PS5
- **DirectMesh on consoles whose GPU reports `1002:13db`:** `ps5-directmesh` and `bootc/mesa/directmesh/0001` accepted only `13fb`, so on those PS5s and Slims the launcher fell back to the system driver and DirectMesh's own detection stayed off (issue #62, rdmrocha; DirectMesh works there when forced). Both ids now, as `patches/ps5-gpu.patch` already does; the Pro's ids stay out
- **`ps5-m2-install` says how to prepare the M.2** when it has no Linux partition: the commands to build and run `m2_init`, and not to run `ps5-linux-tools`' `install.sh`, which adds a second fan and CPU control
- `/usr/lib/modprobe.d/ps5.conf` said "power saving off" for `ps_mode=0`, which is the IW620 firmware's default and has power saving on; the comment now says so and why (`ps_mode=2` put the driver into reset loops under load). The value is unchanged

## [v2.13] – 2026-11-12
> Pre-release. What the loader reads from the PS5 reaches Linux in the initrd: a PS5 Pro has 60 compute units from the first start, and starts without a USB drive get Wi-Fi firmware and pairings.
- **The loader appends what it dumps to the initrd** (`loader/patches/0005`). It dumps the PS5 Pro GPU firmware, the IW620 Wi-Fi firmware and the Bluetooth pairing export next to the initrd it loaded, and Linux picked them up from the boot partition later: the GPU firmware only on the start after (`ps5-stage-viola-fw` appended it to the boot partition's initrd), and none of them when the boot files are in `/data/PS5/Linux`, which Linux can't read. A Pro started that way ran as a base PS5, 36 compute units and no GPU clock governor (the PS5 Pro report of the GPU stuck at 500 MHz). The loader now appends a newc archive to the initrd in memory: the GPU firmware where amdgpu loads it, the Wi-Fi firmware and the pairing export under `/ps5` in the boot directory's layout. Each part goes in whole or not at all; with nothing to add, the initrd is unchanged. The initrd buffer keeps 8 MiB for it. Tested on this side: against a real dracut initramfs in seven cases under ASan/UBSan, the archive unpacking to the dumped files byte for byte with the intended modes (the GPU part as the script's archive); the loader build passes its checks (shellcode headers byte-identical, no new warnings)
- **`ps5-dumps`, a dracut module,** copies `/ps5` to `/run/ps5` before the initramfs ends, and the appended GPU firmware to `/run/ps5/lib/firmware/amdgpu/`: the boot partition's layout. `ps5-stage-firmware` (the image build adds `/run/ps5` to its search list, with a build check) and `ps5-bt-import` look there first, then on the boot partition as before; after importing from `/run/ps5`, `ps5-bt-import` deletes the export on the boot partition, as the importer does with the copy it reads. The image build checks the module is in the initramfs. `ps5-report` lists what arrived in `/run/ps5`
- **Warm reboots keep the PS5 Pro GPU firmware:** `ps5-kexec` starts the boot partition's initrd without the loader, and that initrd no longer carries the firmware; it now appends the same archive from `/run/ps5` in memory (a memfd) when all eight files are there, and loads the initrd as is otherwise. Tested on a real initramfs: the archive walks and unpacks like the loader's
- **`ps5-stage-viola-fw` is gone,** and with it the `ps5.viola_cp=cs2` option. Legacy updates disable and delete it, its state file and `initrd.img.noviola`; `ps5-bootc-sync` removes a leftover `initrd.img.noviola`
- Rebase for X.Y: rmux's default branch (`shitshow` at `8de2aff`) and soniciso1's loader (`main` at `9ffe824`) are unchanged since the pins, so nothing moved

## [v2.12.1] – 2026-11-11
> Pre-release. 4K120 is no longer withdrawn by a link check that outlived its link.
- **The 4K120 link check ends when a modeset begins** (`patches/ps5-display.patch`, `drivers/ps5/hdmi.c`). After a 4K120 setup the driver polls the bridge for up to 5 s and, if the FRL link isn't up, stops offering 4K120 for that display until another EDID arrives or the kernel restarts. That rule is unchanged. The check was only ended by the next video setup, at its end: a modeset that takes the link down without a setup after it (the commit's first block mutes and re-initialises the bridge for the new or the old stream; the setup runs only with a new stream), or an output going down, left it polling a link that was taken down on purpose, and it withdrew 4K120. It also read its sequence number when it started, 1.5 s after being queued, so a modeset inside that time didn't end it either. `sceHdmiDeviceSetVideoMute(1)`, which every modeset begins with and nothing else calls, now cancels a queued check and invalidates a running one; the increment at the end of the setup is gone. Reported after a switch from Game Mode to Desktop: `4K120 link didn't come up (0x7019=00)` 6.7 s after a setup, after eight links that came up, with the output still marked active in 4K120 and no setup logged in between. The case fits; it is not confirmed on the console yet

## [v2.12] – 2026-11-11
